# @monologg/api

The running Fastify backend server for Monologg.

## Implemented in Phase 3

- **Fastify Server Scaffold**: Configured with CORS (locked to client origin), Helmet (secure headers), global rate limiting (100 requests per minute per IP), standard HTTP error helpers (`@fastify/sensible`), structured JSON logging (`pino-pretty` in development), and a central error handler that prevents stack trace leaks in production.
- **Boot-Time Env Validation**: Environment variables (`.env`) are parsed and validated using a Zod schema at boot (`src/config/env.ts`). The server fails fast with a clear explanation if variables are missing or misconfigured.
- **Provider Interface Pattern**: Every external integration is defined via a TypeScript interface with a deterministic mock implementation (`providers/*.mock.ts`) and a real stub implementation (`providers/*.real.ts`) for subsequent phases:
  - `PaymentProvider` (Phase 6: Paystack-first, no Fincra `// TODO(conflict:X1)`)
  - `KycProvider` (Phase 7: Smile Identity)
  - `AiTaggingProvider` (Phase 7: Style/vibe tagging only, separate from identity verification `// TODO(conflict:X3)`)
  - `CalendarProvider` (Phase 8: Google Calendar + Meet)
  - `NotifyProvider` (Phase 9: SendGrid + Twilio)
  The registry (`src/providers/index.ts`) resolves providers to mocks under test mode or per configuration flag.
- **Health Check Route**: `GET /api/v1/health` performs a query (`SELECT 1`) against Supabase to check database status, returning `503` if the database is down.
- **Fee Computation**: Centralized fee-split math in `src/services/fees.ts` that enforces the platform splits (11% talent / 15% client, `// TODO(conflict:X2)`). Uses integer minor units (kobo/cents) to prevent rounding drift.

## Implemented in Phase 4

- **Auth endpoints** (`/api/v1/auth/*`): `register`, `login`, `refresh`, `logout`, `verify-email`, `forgot-password`, `reset-password` (`src/routes/auth.ts`). Generic error messages throughout to avoid user enumeration; `login`/`forgot-password` are rate-limited (10 req / 15 min per IP).
- **Passwords**: argon2id (`src/services/auth.ts`). Never stored, logged, or returned in plaintext.
- **Tokens**: short-lived (~15 min) access JWT + rotating (~30 day) refresh JWT. Refresh tokens are stored hashed (SHA-256) in `RefreshToken`; reuse of an already-rotated token revokes the entire token family. `CacheProvider` (`src/providers/cache.*` — in-memory mock / Redis real) backs the revocation denylist and short-lived verify/reset tokens.
- **Auth middleware** (`src/middlewares/auth.ts`): `requireAuth` (valid access token → 401), `requireRole('TALENT'|'CLIENT')` (→ 403), `requireOwner('user'|'creator'|'client', paramName)` (→ 403 not-owned, 404 not-found). Applied throughout Phase 5's domain routes below.
- **Client wiring** (`apps/web`): `api-client.ts` gained `register`/`login`/`logout`/`forgotPassword`/`isAuthenticated`; every live-mode request now attaches the access token and retries once on a 401 via silent refresh. `AuthFlow.tsx` calls these; a `RequireAuth` route guard wraps the six pages that need a session. Both are no-ops in the default `VITE_API_MODE=mock`.

## Implemented in Phase 5

- **Domain resources** — all owner/participant-scoped and paginated (`src/lib/pagination.ts`, `{data, page, pageSize, total, totalPages}`):
  - `creators` (`routes/creators.ts`) — `GET/PATCH /creators/me` (styleTags/verification aren't even in the update schema — X3 by omission, not a runtime check); `POST /creators/me/media/presign` (video/audio only, ≤150MB, via the new `StorageProvider` seam — mock local-disk fronted by a real `PUT /uploads/local/:token` route, real S3-compatible stub).
  - `rate-cards`, `availability` (`routes/rateCards.ts`, `routes/availability.ts`) — owner-scoped CRUD.
  - `briefs` (`routes/briefs.ts`) — client-owned CRUD. Schema gained `Brief.status` (`DRAFT|ACTIVE|IN_REVIEW|CLOSED`) this phase — not in the original Phase 2 listing, added since the resource needs a lifecycle field to be meaningful.
  - `talent` (`routes/talent.ts`) — public discovery, no auth. Filters: `niche`, `tag` (styleTags), `location`, `minPrice`/`maxPrice`.
  - `bookings` (`routes/bookings.ts`) — `POST` creates in `PENDING_PAYMENT` with fees always derived from `services/fees.ts`'s `computeFees()`, never client-supplied; `GET ?role=talent|client` lists own bookings; `PATCH /:id/cancel` uses the state machine.
  - `order-rooms` (`routes/orderRooms.ts`) — participant-scoped messages, `GET`/`POST /order-rooms/:bookingId/messages`.
- **Booking state machine** (`src/services/booking.ts`): a `LEGAL_TRANSITIONS` map + `assertLegalTransition()` reject illegal moves (e.g. `PENDING_PAYMENT → PAYMENT_RELEASED` directly) with `IllegalBookingTransitionError`. Only `PENDING_PAYMENT → CANCELLED` has a route so far — the rest (`ESCROW_LOCKED`, etc.) are triggered by Phase 6's payment webhook and later delivery/dispute flows, but the full legal-transition graph is defined and enforced now.
- **Response shapes are display-mapped, not raw Prisma rows** — `talent`/`rate-cards`/`briefs`/`bookings` all map real schema fields into the shape `apps/web`'s types expect (e.g. `Creator.niche` enum → a human label, `RateCard.basePriceAmount` → a formatted `"₦28,000"` string). Fields with no real backing data are honest placeholders, not fabricated: `Talent.rating`/`reviews` are `0` (no review system exists in any phase), `ClientProject.applicants` is `0` (no application system until Phase 14).

## Implemented in Phase 6

- **`PaymentProvider.real`** (`src/providers/payment.real.ts`) — a genuine Paystack integration (`/transaction/initialize`, `/transaction/verify`, `/refund`, HMAC-SHA512 webhook verification), selected via `PAYMENT_PROVIDER=paystack`. `payment.stripe.ts`/`payment.airwallex.ts` stub the same interface for later regions (`config/paymentRails.ts` maps countries to a provider) — never "fincra" (X1). Real payouts (`releaseFunds`) throw a clearly-flagged, descriptive error: Paystack transfers need a `recipient_code` from creator bank details, which no phase through Phase 6 collects — beta's ledger-hold model treats the internal `PAYMENT_RELEASED` state as authoritative, with the actual bank transfer reconciled manually until a payout-onboarding phase exists.
- **Ledger-based escrow** (`src/services/payment.ts`) — `POST /bookings/:id/pay` (`initEscrowForBooking`) charges the client's `base + clientFee` total and returns a Paystack checkout URL; it never advances `BookingState` itself. Only `POST /api/v1/webhooks/paystack` (`processPaystackWebhookEvent`) — signature-verified, idempotent — sets `ESCROW_LOCKED`. A client-side "payment succeeded" redirect is purely advisory; there is no endpoint anywhere that lets it move state on its own.
- **Idempotency, without a generic key-store table** — each money-moving path is guarded by the DB mechanism that actually fits it: `Payment.bookingId`/`providerRef` are `@unique`; `PaymentEvent` has a `@@unique([paymentId, type, eventId])` constraint so a replayed webhook's insert hits a unique-violation (Prisma `P2002`) and no-ops instead of reprocessing; `releaseEscrowForBooking`/`refundEscrowForBooking` atomically claim the transition via a conditional `updateMany` (`WHERE status = 'ESCROW_HELD'`) *before* calling the provider — a concurrent second caller sees zero rows affected and no-ops rather than double-paying. `PaymentStatus` gained two transient states, `RELEASING`/`REFUNDING`, to make that claim window observable and rollback-able if the provider call fails.
- **Booking routes gained the rest of the money lifecycle** (`routes/bookings.ts`): `POST /:id/pay`, `PATCH /:id/deliver` (talent), `PATCH /:id/approve` (client — releases escrow), `PATCH /:id/dispute` (either participant), `POST /:id/refund` (dispute resolution placeholder — no admin/adjudication flow exists in any phase yet, so either participant can call it while `DISPUTED`).
- **Known, deliberately-left-open gap:** `apps/web/src/app/pages/Checkout.tsx` (the prototype checkout screen) is **not wired to any of this** — it still runs its original scripted 2.5s delay and still says "FINCRA" three times. Phase 6's kickoff scope was API-only; rewiring the frontend was explicitly deferred rather than folded in silently (see `handoff/log.md` Session 16).

## Implemented in Phase 7

- **`KycProvider` (`src/services/kyc.ts`)** — the only code path that writes `Creator.verification`. `POST /creators/me/verify` starts a check (409 if one's already `PROCESSING`, or the creator is already `VERIFIED`; freely retriable after `FAILED`); `GET /creators/me/verify` polls `KycProvider.getStatus` and only writes on an actual `PROCESSING → VERIFIED|FAILED` transition. Attempts are recorded in `KycCheck`.
- **`AiTaggingProvider` (`src/services/aiTagging.ts`)** — the only code path that writes `Creator.styleTags` (merged/deduped, never overwritten). No dedicated job queue exists yet (Phase 9's BullMQ work); `POST /creators/me/media/:id/confirm` synchronously claims `QUEUED → TAGGING` then runs the provider call + `DONE`/`FAILED` finalization in the background. `GET /creators/me/media/:id` polls the real `taggingStatus` — this is what `apps/web` now drives its UI from, not a fixed timer.
- **X3 enforced at three layers**: schema (`MediaAsset.taggingStatus` vs `Creator.verification` are separate columns/enums, asserted in `prisma/schema.test.ts`), service (each service only ever calls `prisma.creator.update` with its own field — asserted in `services/kyc.test.ts` / `services/aiTagging.test.ts`), and copy (`apps/web`'s `x3CopyAudit.test.ts` — see below).
- **`apps/web` copy audit**: `CreatorOnboarding.tsx`'s old "Thespian AI Verified" scripted animation conflated AI tagging with identity verification. Rewired to real job-state polling in `live` mode (mock mode keeps a local timed simulation, no network — same seam contract as every other mock-mode screen), and reworded everywhere: the finished state now reads "Style Tags Generated," never "Verified." The same conflation was found and fixed on `Settings.tsx`, `TalentDashboard.tsx`, `LandingPage.tsx`, `AuthFlow.tsx`, and `ClientDashboard.tsx`.
- **Known, deliberately-left-open gap:** no screen anywhere collects the legal name/DOB/country/ID-type/ID-number `POST /creators/me/verify` needs — a creator can't yet self-serve identity verification from the UI. The endpoints are real and fully tested; building an input form wasn't in this phase's kickoff scope (see `handoff/log.md` Session 17, same shape as the Phase 6 `Checkout.tsx` gap above).

## Implemented in Phase 8

- **Google OAuth, per user, refresh token encrypted at rest** (`src/lib/encryption.ts`, AES-256-GCM; `CalendarConnection.encryptedRefreshToken`). `POST /calendar/connect` mints a one-time, cache-backed `state` token (never the raw userId — an OAuth `state` a browser query string carries can't be trusted, so it's opaque and mapped server-side) and returns Google's consent URL with minimal scopes (`calendar.events` + `calendar.freebusy`, `access_type=offline`, `prompt=consent`). `GET /calendar/callback` is public (Google redirects the *browser* here, with no bearer token) — it resolves `state` back to a userId, exchanges the code, and encrypts the refresh token before it ever reaches the database or a log line.
- **`CalendarProvider.real` (`src/providers/calendar.real.ts`)** — raw fetch against Google's OAuth/Calendar REST endpoints (no SDK dependency, matching `payment.real.ts`'s style). Access tokens are never cached: every real call re-exchanges the stored refresh token first, which *is* the "handle expiry" behavior — there's no separate access-token-expired state to track. `pushAvailability` creates/PATCHes a Calendar event per `AvailabilityBlock`; `getBusyTimes` runs a `freeBusy.query` (this is the hook Phase 13's `getOpenSlots` will call); `createMeet` creates an event with `conferenceData` and returns the real Meet link.
- **Graceful revoke/expiry handling** — Google's `invalid_grant` response on a refresh-token exchange is translated into a typed `CalendarAuthRevokedError`. `services/calendar.ts` catches it everywhere, flips `CalendarConnection.status` to `REVOKED`, and surfaces a `CalendarReconnectRequiredError` (routes map this to `409 { reconnectRequired: true }`) — never a raw 500. `createMeetForBooking` (called best-effort from the payment webhook on escrow lock) degrades to a no-op `null` on either a missing or revoked connection: a booking never fails because Meet creation did.
- **New routes**: `POST /calendar/connect`, `GET /calendar/callback` (public), `POST /calendar/disconnect`, `GET /calendar/status`, `GET /calendar/busy-times?date=`, `POST /availability/:id/sync-calendar`.
- **Known, deliberately-left-open gap:** this phase is the provider layer only, by its own kickoff scope — no `apps/web` screen calls any of these endpoints yet. `TalentDashboard.tsx`'s "Availability" tab still has no real calendar sync, and there's no Meet-link UI anywhere in the Order Room. Both are intentionally deferred to Phase 13, which owns the rich availability UX these endpoints exist to support (see `handoff/log.md` Session 18).

## Implemented in Phase 9

- **In-app notifications are real** — `NotifyProvider.inApp` (both mock and real) persists to `Notification` via a shared helper (`src/providers/notify.shared.ts`); there's no meaningful "mock in-app notification" distinct from a real one, since the table is our own DB either way. `GET /notifications` (paginated, `unreadCount` alongside the envelope) and `POST /notifications/:id/read` (owner-scoped, idempotent) are the read/ack side (`src/services/notifications.ts`).
- **Email (SendGrid) + SMS (Twilio) are real** (`src/providers/notify.real.ts`, raw fetch, no SDK) — `email()` renders a template via the new registry (`src/lib/notificationTemplates.ts`; "localisable" is a real, load-bearing mechanism — every renderer takes a `locale` and falls back to `en` — but only `en` content ships, same proportionate-stub pattern as `payment.stripe.ts`). `verify_email`/`reset_password` (referenced by Phase 4's `auth.ts` since the start, never actually implemented until now) now render for real too.
- **Async delivery via a job queue, with retry + backoff** (`src/jobs/` — a new top-level concern, not a `*Provider`, per `features.md`'s own architecture section listing "jobs" separately). `notificationQueue.mock.ts` is an in-process retry loop (3 attempts, short exponential backoff) for dev/test; `notificationQueue.real.ts` is BullMQ-on-Redis (`attempts: 3, backoff: exponential 1s`), selected via `JOB_QUEUE_PROVIDER=bullmq`. Both call the exact same processor (`notificationWorker.ts`) — only the retry/scheduling mechanism differs.
- **`NotificationPreference`** — per-user, per-channel (`emailEnabled`/`smsEnabled`) opt-out, `GET`/`PATCH /notifications/preferences`. No row = both enabled by default. In-app is never gated by this (not the legally-sensitive channel; email/SMS unsubscribe is) — only `enqueueEmailNotification`/`enqueueSmsNotification` check it.
- **Domain events now actually publish notifications**: `booking_created` (new — `POST /bookings`), `deliverables_provided` (new — `PATCH /bookings/:id/deliver`), `new_message` (new — `POST /order-rooms/:id/messages`, notifies the *other* participant, never the sender), plus email added alongside the *existing* Phase 6/7 in-app-only calls: `payment_escrow_locked`, `payment_released`, `payment_refunded` (`services/payment.ts`), `kyc_verified`/`kyc_failed` (`services/kyc.ts`). `tagging_done`/`calendar_disconnected` stay in-app-only — not worth an email.
- **`User.phone` (new, nullable)** — SMS has a real recipient column to key off, but no phase through Phase 9 collects one at registration/onboarding. `enqueueSmsNotification` skips silently (not an error) when it's null — a real, flagged gap, not a fabricated data source.
- **Tests, the gate's own list, all covered**: `jobs/notificationQueue.mock.test.ts` (retry-with-backoff, gives-up-after-max-attempts, fire-and-forget), `providers/notify.real.test.ts` + `providers/notify.shared.test.ts` (SendGrid/Twilio HTTP mechanics, template rendering, in-app persistence), `services/notifications.test.ts` (dispatch + preference-respecting, **user-scoping** on list/unread/mark-read — a cross-account leakage attempt is explicitly asserted to 404, not succeed), `routes/notifications.test.ts`, and new assertions in `routes/bookings.test.ts`/`routes/orderRooms.test.ts` for the three new domain-event hooks.
- **Known, deliberately-left-open gap:** `Settings.tsx`'s existing "Notifications" toggle UI (5 local categories: bookings/messages/payments/reminders/marketing) is still fully local state, unwired to `GET/PATCH /notifications/preferences` — but that entire screen has no backend wiring of any kind yet (pre-existing, not introduced by this phase), and its category granularity doesn't map onto the simpler `emailEnabled`/`smsEnabled` model this phase built. Wiring it is a `Settings.tsx`-wide pass, not something to fold in here.

## Implemented in Phase 10

- **Transaction history is real** (`GET /transactions`, `src/services/transactions.ts`) — derived read-only from `Payment` + `Booking`, no new ledger table. Owner-scoped by looking up the caller's own `Creator`/`Client` profile(s) and only querying bookings where they're a participant; a `direction` field (`"payment"` | `"payout"`) disambiguates which fee math applies to a given row (a client was charged base+clientFee; a creator nets base−talentFee) since the *same* Payment row means something different depending which side you're on. Paginated and filterable by `state` (PaymentStatus) and `direction`.
- **Help & support is real** (`POST`/`GET /support/tickets`, new `SupportTicket` model, `src/services/support.ts`) — owner-scoped. On submission: a confirmation email to the submitter via the existing queued `enqueueEmailNotification` path, plus an optional relay to an internal inbox if `SUPPORT_INBOX_EMAIL` is configured (best-effort — a relay failure never fails ticket creation). The FAQ/knowledge-base content is static, per the spec's own explicit allowance ("static or CMS-backed") — no CMS exists in any phase.
- **Terms & privacy acceptance is real** — new `TermsAcceptance` model (one row per acceptance event, never updated in place, so consent history stays auditable per the Phase 10 guardrail). `POST /auth/register` now *requires* `acceptedTermsVersion` (mirrors `AuthFlow.tsx`'s existing hard checkbox gate, previously never actually sent to the backend) and records it with a DB-default timestamp inside the same registration transaction. `CURRENT_TERMS_VERSION` is a single shared constant in `packages/types` — the one source both apps read, so the version the frontend displays/sends and the version the backend can validate against can't drift into two hardcoded strings.
- **Legal page content is an explicitly-flagged draft, not real legal copy** — `apps/web`'s new `/legal/terms` and `/legal/privacy` pages are real, versioned, and structurally complete, but the prose was never reviewed by counsel. Shipping fabricated "binding" legal text under an AI's byline would be actively wrong, not just incomplete, so the page itself displays a visible draft notice rather than only flagging this in a code comment.
- **Tests, the gate's own list, all covered**: `services/transactions.test.ts` (7, including explicit **owner-scoping** assertions — a client only ever sees `booking: {OR: [{clientId}]}`, a creator only `{creatorId}`, direction-filtering never crosses into the other side even for a user with both profiles) + `routes/transactions.test.ts` (4), `services/support.test.ts` (5) + `routes/support.test.ts` (5, including owner-scoped listing), and new `routes/auth.test.ts` assertions for **terms acceptance with version + timestamp** (asserts `TermsAcceptance.create` receives the exact version sent, and that `acceptedAt` is left to the DB default rather than a client-suppliable value) plus a 400 test for registering with no acceptance at all.
- **A real cross-package typecheck gap surfaced and fixed along the way**: `apps/api` had never imported from `@monologg/types` before this phase. Doing so (for `CURRENT_TERMS_VERSION`) surfaced that `packages/types/src/index.ts`'s relative exports lacked the explicit `.js` extensions `apps/api`'s `NodeNext` module resolution requires — invisible until now because `apps/web`'s `bundler` resolution never needed them. Fixed by adding the extensions (harmless under `bundler` resolution too).

## Implemented in Phase 12

**Goal of this phase, per features.md:** make what already exists (Phases 0–11) production-ready — hardened, tested, observable, and deployable. Nothing here is a new feature; it's the consolidation pass the PRD itself describes as backstopping every prior phase's own tests, not replacing them.

- **Security (OWASP pass)**:
  - **Headers/CORS/rate-limiting were already real as of Phase 3/4** (`@fastify/helmet`, `@fastify/cors` locked to `CORS_ORIGIN`, `@fastify/rate-limit` global 100/min + auth-specific 10/15min). This phase tightened the one thing that was a placeholder: Helmet's CSP was `contentSecurityPolicy: false` with a "tighten per-route if serving HTML" comment — since apps/api never serves HTML in any phase, it's now `default-src 'none'; frame-ancestors 'none'` outright (`src/app.ts`).
  - **Log redaction** (`src/app.ts`): pino's `redact` option now scrubs `req.headers.authorization`/`cookie` and any `password`/`passwordHash`/`*token*`/`idNumber` key at any depth. Defense-in-depth, not a fix for an existing leak — `routes/auth.test.ts`'s Phase-4 "Sanitized Logs" test already proved nothing logs a raw password/token today (Fastify's default serializers never include the request body); this is what stops a *future* debug log line from becoming one.
  - **CSRF**: not applicable, verified rather than assumed — every session in this codebase is a bearer JWT in the `Authorization` header or request body (`services/auth.ts`), and no route anywhere registers `@fastify/cookie` or sets a session cookie. CSRF requires an ambient credential a browser attaches automatically; there isn't one here.
  - **Production DB URL enforcement** (`src/config/env.ts`'s new `checkProductionDbUrls`, gated to `NODE_ENV=production` only): fails boot with a specific message if `DATABASE_URL` isn't the Supabase transaction pooler (port 6543 + `pgbouncer=true`) or `DIRECT_URL` isn't the session pooler (port 5432, no `pgbouncer=true`), or if the two are identical. These are easy to swap by accident since both point at the same Supabase host — see "Supabase operational notes" below for why the distinction matters.
  - **KYC PII: minimal retention, not "encrypt it once stored"** — audited (`prisma/schema.test.ts`, `services/kyc.persistence` assertion in `services/kyc.test.ts`) and locked in as tests: `KycCheck` has no column for legal name/DOB/ID number at all (only `provider`/`providerRef`/`status`); `startKycCheck` passes the full `KycData` to `KycProvider.startCheck` and nothing else. There's nothing at rest to encrypt because it was never written to a row — a stronger NDPA posture than encryption for data this sensitive. (Calendar refresh tokens, which genuinely are stored, stay AES-256-GCM-encrypted per Phase 8's `src/lib/encryption.ts` — unchanged.)
  - **Dependency audit**: `pnpm audit --audit-level=high` (root `pnpm run audit`) is now a CI-blocking step. Fixed by bumping: `react-router` 7.13.0 → 7.18.2, `vite` 6.3.5 → 6.3.7 (resolved to 6.4.3 by pnpm's resolver) — both verified with a full typecheck/test/build pass after bumping, not just installed and assumed safe. Two advisories remain and are **reviewed, deliberate exceptions**, not oversights, allowlisted explicitly in `package.json`'s `pnpm.auditConfig.ignoreGhsas` (visible in `pnpm audit` output as "ignored," never silently hidden):
    - `GHSA-qwww-vcr4-c8h2` — react-router RSC-mode CSRF bypass, fixed only at 8.3.0+. This app uses none of react-router's RSC/`unstable_middleware` surface anywhere (confirmed by grep across `apps/web/src`); jumping a major version two months after its release, in a hardening phase with no allocated regression-testing budget for a routing rewrite, was judged the worse risk.
    - `GHSA-mh99-v99m-4gvg` — a `brace-expansion` DoS via unbounded glob-pattern expansion, reachable only through eslint's and vitest's own dev-tooling dependency trees. **Tried and reverted a `pnpm.overrides` pin to force every instance to the newest release line** — it silently broke ESLint at runtime (`TypeError: expand is not a function`, the older API shape `minimatch@3` still expects) before this was caught by re-running `pnpm run lint` after the change, never shipped. Every glob pattern in this codebase's own config is a hardcoded string (`src/**/*.test.ts`, etc.), never attacker- or user-controlled input, so the DoS has no real trigger path here — allowlisting the already-broken-nothing state was judged better than a version pin already proven to break tooling.
    A human should revisit both if/when a v8 `react-router` migration is deliberately scheduled, or if eslint/vitest's own upstream dependency trees naturally move past the vulnerable `brace-expansion` range on their own.
- **Testing**:
  - **Coverage thresholds** (`apps/api/vitest.config.ts`, `pnpm run test:coverage`): a modest 60% global floor, with real gates on the money/auth/state modules the PRD names explicitly — `services/fees.ts` (95%), `services/payment.ts` (85%), `services/auth.ts` + `middlewares/auth.ts` (90%), `services/booking.ts` (90%). Closing the one gap this surfaced (`middlewares/auth.ts` was at 79%) meant adding real tests for previously-untested branches — `requireOwner`'s missing-param and client-not-found paths, and both `requireRole`/`requireOwner`'s defensive "called without `requireAuth` having run first" guards — not lowering the bar to match existing coverage.
  - **Cross-cutting hardening tests** (`src/app.hardening.test.ts`, new): Helmet headers and the strict CSP present on an ordinary route, CORS reflecting the configured origin and never an arbitrary one, the new `x-request-id` header being present and unique per request, and both new routes below. (Rate-limit enforcement and no-PII-in-logs already had dedicated coverage from Phase 4's `routes/auth.test.ts` — not duplicated here.)
  - **E2E happy path** (`src/e2e.happyPath.test.ts`, new): a single continuous flow — create booking → initiate escrow → Paystack webhook confirms → talent delivers → client approves-and-releases — run against one stateful mocked-Prisma fake so each step reads back what the previous step actually wrote, the way a real database would (existing route tests reset their mocks fresh per test and don't prove the seams connect). A second test in the same file asserts the negative: with no webhook call, the booking stays `PENDING_PAYMENT` and an approve attempt 409s — proving a client-side "success" redirect still can't substitute for the webhook, Phase 6's own authority guardrail, now under continuous state rather than an isolated call. The literal "register" leg is Phase 4's `routes/auth.test.ts` "Full end-to-end chain" test, not re-mocked here — see the new file's header comment for why splitting it this way tests strictly more than one giant combined file would.
- **Observability**:
  - **Request IDs**: Fastify already assigned a per-request ID to its own log lines; `src/app.ts` now also echoes it as an `x-request-id` response header, so a support ticket (Phase 10) or a client-reported error can be grepped straight to its log lines.
  - **`GET /api/v1/ready`** (`src/routes/health.ts`, new, alongside the existing `/health`): same DB round-trip — for this single-process API, "alive" and "able to serve real traffic" both reduce to "can reach Postgres," so there's no meaningfully different check to write yet. Kept as a genuinely separate route (not an alias) so a deploy target wiring liveness/readiness probes differently doesn't have to share one, and so it can diverge later without a breaking route change.
  - **`GET /api/v1/metrics`** (`src/routes/metrics.ts` + `src/lib/metrics.ts`, new): in-process JSON counters — request volume by status class (⇒ request/error rate), and payment outcomes (`escrow_locked`/`released`/`refunded`/`release_failed`/`refund_failed`, ⇒ payment success rate over terminal outcomes). Deliberately not Prometheus text format or a real metrics backend — none exists in any prior phase, and standing one up is out of this phase's scope; this is the simplest thing that makes "request rate, error rate, payment success rate" (the PRD's own words) computable from a scrape interval. ## Implemented in Phase 12A

Three additive extensions to the storefront and onboarding — additive-only migration (`20260730204433_phase12a_media_kit_verification_attributes`), nothing from Phases 0–12 renamed, dropped, or altered. Ran against the real Supabase project (this developer has direct access this session); the backfill step gave all 8 pre-existing creators an AUTO-mode `MediaKit` row, verified with a direct count query, not just trusted from the migration's exit code.

- **12A.1 — Media Kit** (`src/services/mediaKit.ts`, `src/routes/mediaKit.ts`): every creator gets a `MediaKit` row (`mode: AUTO | UPLOAD`) at registration (`routes/auth.ts`'s nested `mediaKit: { create: {} }`) and via the migration backfill for everyone before that. **AUTO** renders a real PDF server-side with `pdf-lib` (not Puppeteer — no headless-Chrome binary dependency to manage across dev/Docker/Railway) from PUBLIC data only: name, niche, location, style tags, badges, bio, rate cards ("on request" if none), a `monologg.co/{creatorId}` contact line. No headshot or showcase-thumbnail image is embedded — no phase's schema stores a creator photo or extracts a video still-frame, so an initials mark stands in rather than fabricating an image; a real screenshot/build-time smoke test of the renderer (not just unit tests) caught a genuine bug before it shipped: pdf-lib's standard fonts use WinAnsi encoding, which has no Naira glyph — `formatMoney()`'s "₦28,000" would have crashed PDF generation for any NGN rate card. Fixed with a PDF-specific formatter using currency codes ("NGN 28,000") instead of chasing a custom Unicode font embed for one glyph. **UPLOAD** validates real PDF magic bytes (`%PDF-`, never trusts a filename), the 20MB cap, and a virus scan — in that order, so an oversized or fake-PDF file never reaches the scanner — via a new `ScannerProvider` seam (mock detects the real EICAR antivirus test string; real is an honest `throw "not yet implemented"` stub, same shape as `kyc.real.ts` before Smile Identity existed). Reverting to AUTO never deletes the uploaded file or changes the public URL (`GET /creators/:id/media-kit.pdf`) — only the `mode` flag flips.
- **12A.2 — Verification video** (`src/lib/videoDuration.ts`, `src/services/verificationRecording.ts`, `src/routes/verification.ts`): a new `VerificationRecording` model, deliberately zero relation to `KycCheck` — the X3 invariant (Phase 7: style tags vs. identity KYC) applied to a new axis, performance review vs. identity. The pre-record guideline acknowledgment is cache-backed (mirrors `services/calendar.ts`'s OAuth `state`-token pattern) rather than a DB column — a short-lived "did they just tick the box" flag, consumed by the very next upload. The **server-authoritative duration check** the spec calls for is a genuine, from-spec ISO-BMFF (MP4 container) box parser (`lib/videoDuration.ts`) — not a wrapper around `ffprobe`/`ffmpeg` (no such binary is guaranteed on any deploy target this repo runs on) and not trusting a client-side timer. It walks `moov` → `mvhd` and reads the real `timescale`/`duration` fields per the ISO/IEC 14496-12 spec, both v0 (32-bit) and v1 (64-bit) box shapes, with 8 unit tests constructing real box bytes by hand. A > 90s upload 422s with `{ reRecord: true, durationSec }`, distinct from a generic 400, so the client can show a specific re-record prompt. Reviewer decisions (`PATCH /verification-recordings/:id/review`) are a **known, flagged gap**, same shape as Phase 6's dispute/refund endpoint: no admin/moderator role system exists in any phase through 12A, so this is reachable by any authenticated user, not gated to real reviewers — documented here and in the route's own comment, not silently assumed away.
- **12A.3 — Physical attributes** (`src/services/attributes.ts`, `src/routes/attributes.ts`, `routes/talent.ts`'s search extension): a new `PhysicalAttributes` model enforcing all six PRD privacy non-negotiables, each traceable to a specific code path: (1) every field optional in both schema and zod; (2) ranges/enums, never raw numeric height/weight/age (locked in by a schema test); (3) default visibility is `SEARCHABLE`, and a field's **first-ever** explicit value can never save as `PUBLIC` even if that's what was requested — silently downgraded, tracked **per field** (not per row), so a talent adding hair color next month still gets the same first-save protection their height got on day one, even though the row already existed; (4) `consentVersion`/`consentedAt` captured on first save and on any consent-version change, untouched on an ordinary field edit under the same version; (5) `DELETE` hard-deletes the row (right-to-erasure), idempotent; (6) `publicAttributesOf()` is pure filtering with no score/rank field anywhere in its output shape — locked in by an explicit test. The value-set enums (height/weight/age ranges, build, complexion, hair/eye color, gender presentation, shoe size unit) are `TODO(conflict:X6)` — the phase brief said "enums per PRD 12A.3" without enumerating them, so these are a reasonable casting-industry-shaped interpretation flagged for human confirmation, the same X1–X5 pattern, not a silently-invented spec. Search (`GET /talent`) filters application-side, not via a Prisma JSON-path query against the `visibility` map — deliberately, since this repo's live-DB integration suite isn't CI-gated (see "Database" section below) and application-side filtering is fully covered by the fast, mocked-Prisma gate; known tradeoff, pagination runs post-filter in memory when any attribute filter is active, correct at this app's current scale, not the shape a large directory would want. A talent is a filter *candidate* whenever a field's visibility isn't `PRIVATE` (`SEARCHABLE` counts); the response *value* is only ever included when that field is `PUBLIC` — "a slim filter can succeed without exposing the label," verified by a test that matches on `SEARCHABLE` and asserts the value is absent from the payload.

## Implemented in Phase 13 (rich availability calendar & time-slot booking, FA-1)

## Supabase operational notes

This project's real Postgres is Supabase (`DATABASE_URL`/`DIRECT_URL` in `.env.example`). Two things a free-tier project does that a paid one doesn't, relevant before any shared/user-facing environment goes live:

- **Free-tier projects pause after ~7 days of inactivity and provide NO backups.** Fine for local development (this repo's own dev database) — actively unsuitable for staging or anything a real user or reviewer might hit unannounced.
- **For any staging/shared environment**: either add a keep-alive (a scheduled job — cron, or a GitHub Action — pinging `GET /api/v1/health` every ~3 days is enough to prevent the pause) **or** upgrade to Supabase Pro ($25/mo), which removes the pause behavior and enables point-in-time-recovery (PITR) backups.
- **Before real users touch this**: plan the move to Pro. The two ceilings this data shape hits first are **file storage (1 GB)** and the **pause behavior** — not the database itself (500 MB is generous for this schema at any realistic beta scale). Don't wait for a storage or pause incident to make this call.
- **`DATABASE_URL` (pooled) vs. `DIRECT_URL` (session/direct)** — see the Phase 3/12 entries above for what each is for. `config/env.ts`'s `checkProductionDbUrls` now enforces the distinction at boot under `NODE_ENV=production` specifically so a misconfigured environment variable fails loudly at deploy time instead of surfacing later as a connection-pool exhaustion incident or a migration that silently can't take an advisory lock.
